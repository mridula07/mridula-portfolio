Designing the system behind a calmer inbox

MailQ is a desktop email client that uses AI to summarize threads and cut through inbox noise. I built its design system from the ground up: a three-tier token architecture, light and dark theming, a documented component library, and developer handoff.

Role
Product designer
Timeline
2 weeks
Tool
Figma, Claude, ChatGPT
Platform
Desktop web

The starting point

MailQ was a take-home assignment to design a desktop email client with an AI feature. The deliverables included the core product screens and a small, component-based design system to support them.

The system only needed to be big enough to build the screens consistently: a few colours, a type scale, and the components the screens actually used.

I decided to go further

Once the core screens were taking shape, I saw an opportunity to go beyond the minimum deliverable, and use it to explore variables, tokens, theming, reusable components, and design-to-development handoff.

A take-home is a safe place to test questions that are hard to test on a live team: what a token architecture costs to maintain, where dark mode should live, and how much documentation a component really needs.

Defining the system

The goal was to create a system that was practical to use, easy to scale, and grounded in the needs of the product rather than built as a collection of UI components in isolation.

01

Part one: Building the foundations

Colour, type and icons: the raw choices everything else is built on.

Colors

I used teal as MailQ’s primary colour to give the product a distinct identity while keeping the interface calm enough for a productivity-focused tool. Instead of a generic grey scale, the neutrals carry a subtle teal hue, so surfaces, borders and text stay connected to the brand without competing with it.

Typography

Type is set in Geist, on a deliberately tight 11–18px scale that steps up by roughly a Major Second. An email client is dense: senders, subjects, timestamps and labels all compete for one row, so the scale gives enough hierarchy to scan without big jumps.

Icons

Icons come from Phosphor, used at 14 and 16px to keep controls compact without losing recognition. Spacing runs on a 4px base from 2 to 32px. Borders are a 1px stroke with 8px and 12px radii in everyday use.

02

Part two: Tokens

The naming system that lets one edit restyle every screen.

Every colour, gap and corner in MailQ comes from a token: a named design decision that screens point at instead of hard-coding a value. There are 222 of them, organised into three layers so that each kind of change happens in exactly one place.

  • 97Primitivesraw values
  • 68Aliascolour roles
  • 57Semanticpurposes
  • 2Themeslight and dark

Three layers, each with one job

Primitives are the raw material: every colour ramp, plus the spacing, radius and border-width scales. They describe what exists, not where it goes.

Alias gives colour a role. Teal becomes primary, grey becomes neutral, red becomes error. If MailQ is ever rebranded, this is the only layer that changes.

Semantic describes purpose, like the fill of an action or the colour of body text. Components only ever use this layer, so no screen refers to a raw colour.

Seamless theme switching through Semantic tokens

I built dark mode into the variables themselves. The Semantic collection has two modes, Light and Dark, so every token carries a value for each theme, and each colour changes only as much as it needs to: body text flips from near-black to near-white, while the teal action colour just gets slightly lighter. Components only ask for tokens, so switching a frame to Dark re-themes everything inside it, with nothing redrawn or recoloured by hand.

03

Part three: Components

The parts every screen is built from, and the sheets that document them.

Every screen built from the same set of parts

Documenting the system

Each component gets one documentation sheet with the same sections, in the same order: an overview, anatomy, variants and properties, behaviour, states and tokens, usage, spacing and sizing, accessibility, and developer handoff.

The states and tokens table is the part people actually use while building, so it gets the most care. Its swatches are bound to the real variables rather than pasted as hex codes, so the documentation can’t drift away from the component it describes.

Design to dev

Token names map one to one to CSS custom properties: slashes become hyphens, so a designer’s text/action/hover is a developer’s var(--text-action-hover). There’s no translation table to maintain.

Every colour a component uses comes from a Semantic token, so dark mode never touches component styles; it only redefines the values underneath.

Putting it to the test

What If the Brand Colour Changes Tomorrow?

Midway through a project, the team decides the brand should be blue instead of teal. In MailQ, that is one edit: the Primitive behind primary. Every token name below it stays the same, and the change flows through on its own.
